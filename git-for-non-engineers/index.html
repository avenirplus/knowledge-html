棚

AI開発での安全な一本道

  1. 現在地を確認git status / いま未保存の変更がないかを見る
  2. 正常なら修正前commit「ここまでは動いていた」という戻り地点を残す
  3. AIに修正を依頼Codexなどが必要なファイルを変更
  4. diff（差分）を確認頼んだ所以外まで変わっていないかを見る
  5. 実際にテスト見た目だけでなく、変更した機能を操作して確認
  6. 修正後commit正常になった新しい状態をセーブ
  7. push → deploy → 本番確認GitHubへ送り、Cloudflare反映後、実際のURLで確認

「変更した」と「完成した」は別

コード変更→commit→push→deploy→本番確認 ✓

たとえば「GitHubにpushした」だけなら、Cloudflare上の本番が正常に動くことまでは確認できていません。工程を分けて考えます。

最重要：秘密をGitに入れない

APIキー、パスワード、SESSION_SECRET、秘密鍵などは、Gitに記録しないのが基本です。

.gitignore
.env
.env.local
node_modules/

.gitignore は「このファイルはGitの記録対象にしないで」という除外リストです。

危険 秘密情報を一度commitすると、今のファイルを削除しても過去の履歴に残ることがあります。漏えいの可能性がある場合は、削除だけで終わらせず鍵の無効化・再発行を検討します。

よくある誤解

「commitした＝完成」？

違います。commitは履歴を残しただけです。push、deploy、本番確認は別工程です。

「GitHub Private＝WebサイトもPrivate」？

違います。GitHubは主にソースコード側の公開範囲。Webサイト側はCloudflare Accessなど、配信側のアクセス制御を別に考えます。

「AIに“元に戻して”と言えばGitはいらない」？

危険です。AIの記憶や推測ではなく、実際のコミット履歴を正本として戻せることがGitの強みです。

「AI作業前は何でも全部commit」？

まずstatusで未完成変更や秘密情報が混ざっていないか確認します。「正常な戻り地点」を作ることが目的です。

1分理解チェック

Q1. commitしたら必ずGitHubにも保存される？

いいえ。GitHubへ送る操作は push です。

Q2. AIが修正したあと、まず見るとよいものは？

diff（差分）。頼んだ変更以外が混ざっていないか確認します。

Q3. .gitignore は何のため？

Gitに記録させたくないファイルを除外するためです。

Q4. GitHubがPrivateならWebサイトも自動でPrivate？

いいえ。コードの公開範囲とWebサイトへのアクセス制御は別です。

最後にこれだけ

Gitを学ぶ目的は、コマンド暗記ではありません。

AIがコードを変えても、何が変わったか分かり、正常だった場所を失わず、安全に前へ進める。

まずは status＝現在地、diff＝変更点、commit＝セーブ、push＝GitHubへ送る の4つが分かれば十分です。
